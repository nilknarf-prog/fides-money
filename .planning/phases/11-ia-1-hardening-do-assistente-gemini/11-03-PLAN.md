<objective>
AI-TELEM-01: `assistant_usage` passa a gravar tokens de entrada/saída + latência por chamada. Fonte: `usageMetadata` da resposta Gemini (`promptTokenCount`, `candidatesTokenCount`) + medição de tempo no servidor. Objetivo: custo real por usuário observável — base dos evals das fases 12–14. NÃO construir dashboard nem agregação: só gravar o dado.

Purpose: hoje `assistant_usage` só conta chamadas (para rate limit). O insert acontece ANTES da chamada Gemini, quando tokens/latência ainda não existem. A abordagem travada (Opção A da pesquisa): manter o insert de contagem e fazer um UPDATE da mesma linha após a resposta, fail-open. Colunas nullable — chamadas antigas e falhas ficam null, sem backfill.

Achado importante: a tabela `assistant_usage` NÃO tem espelho `.sql` no repositório (criada direto no banco via MCP — débito B10). Este plano cria o espelho E aplica os ALTERs no banco.

Output: `supabase/schema.sql` com espelho + ALTERs; `api/assistant.js` capturando id do insert, medindo latência e fazendo o update; migração aplicada no banco via MCP (checkpoint humano).
</objective>

  <action>
    Em `api/assistant.js`, implemente a telemetria sem regressão do rate limit (AI-TELEM-01, Opção A da pesquisa):

    1. Capturar o id do insert: o insert de contagem em `assistant_usage` (hoje `.insert({ user_id })`, só no isFirstCallOfTurn) passa a retornar o id da linha — encadeie `.select('id').single()` e guarde o id numa variável no escopo do handler (ex.: usageRowId), tolerante a erro (se o insert falhar, segue null — fail-open, como hoje).
    2. Medir latência: registre `const t0 = Date.now()` imediatamente antes da chamada Gemini (`gemini.callGemini`), e calcule `latency_ms = Date.now() - t0` logo após a resposta. Cobre só a chamada Gemini (o que interessa para custo/performance do modelo).
    3. Ler tokens: do resultado de `gemini.parseResponse`, use `usageMetadata` — `promptTokenCount` → prompt_tokens, `candidatesTokenCount` → completion_tokens. Tolerar ausência (usageMetadata null em erro → colunas ficam null).
    4. UPDATE fail-open: quando houver usageRowId, faça um `.from('assistant_usage').update({ prompt_tokens, completion_tokens, latency_ms }).eq('id', usageRowId)`. Envolva em tratamento fail-open — telemetria NUNCA pode derrubar a resposta ao usuário (se o update falhar, logar só o erro e seguir, como o insertError atual). Faça o update no caminho de sucesso da resposta; em erro do Gemini, gravar latency_ms com tokens null é aceitável (opcional) — o essencial é não regredir e não bloquear.

    Minimização de dados: gravar APENAS contagens de token + latência. NUNCA gravar o texto do prompt, do contexto ou da resposta (LGPD §9 / Information Disclosure). NÃO mover o insert para depois do Gemini (quebraria o rate limit fail-open). NÃO construir agregação/dashboard.
  </action>
