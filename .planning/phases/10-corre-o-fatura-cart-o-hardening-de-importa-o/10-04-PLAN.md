<objective>
Fechar os 2 BLOCKERS de import (G1 dedup ignora pendentes / destino default errado; G2 import converte pendente→paga / duplica lançada) e o MAJOR G3 (opções de destino + status no modal) do 10-UAT.

Root cause (diagnosticado no UAT):
- `dedupeKey(tx)` = `desc|cents|day|acct` (fides-transacoes.jsx:86-98, WR-03 inclui `acct`). No reimport, o `resolveRowForImport` resolve `acct` para o destino GLOBAL do dropdown (default = 1ª conta / débito), não a conta/cartão de ORIGEM da linha → a chave não bate com a tx existente (cujo `acct` é o card_id) → não é marcada como duplicata → viria marcada p/ importar (duplicaria) e iria pro débito.
- `handleExport` (fides-transacoes.jsx:707) grava na coluna "Conta" `accounts.find(...).name || t.acct` — para cartão, `t.acct` é card_id (não está em `accounts`) → grava o card_id cru, não o NOME. O modal casa `acctNameRaw` por NOME → nunca casa cartão → cai no default débito.
- Write path: `txToRow` (fides-store.jsx:228) faz `STATUS_TO_DB[tx.status] || 'cleared'` — status ausente/indefinido vira **pago** silenciosamente (medo real do usuário: "seriam lançadas como PAGAS").

Correção: (a) export grava o nome do cartão; (b) `resolveRowForImport` resolve o destino POR LINHA a partir de `acctNameRaw` (casa nome→conta/cartão), usando o dropdown só como fallback/override; (c) o modal ganha controle de destino ("Da origem do arquivo" default) + controle de status (do arquivo / pendente / paga), e o confirm sempre envia status explícito.

Purpose: reimport idêntico = 0 gravações; nunca reescrever tx existente; usuário controla destino e status; card_id resolvido.
Output: `assets/fides-transacoes.jsx` com export corrigido, resolução de destino por linha e ImportPreviewModal com opções.
</objective>
