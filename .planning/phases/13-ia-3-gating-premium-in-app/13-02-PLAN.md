<objective>
P1 (pré-requisito de segurança do gate inteiro, sob integridade de GATE-03): a policy RLS de `profiles` (`for all using (auth.uid() = id)`, sem `WITH CHECK` restritivo) permite hoje que QUALQUER usuário autenticado altere o próprio `plan` via client SDK — `window.fidesDb.from('profiles').update({plan:'pro'})` no console vira premium sem pagar. RLS restringe LINHAS, não COLUNAS. Esta plan fecha o buraco com privilégio de coluna nativo do Postgres (REVOKE/GRANT), o padrão oficial do Supabase para column-level security.

Purpose: sem esta trava, o gate de IA (Plans 13-01/13-03) é sólido mas o TIER em si é auto-outorgável — o dado que decide "quem paga" seria editável por quem é controlado (falha de V4 Access Control na origem). Este é o headline threat do RESEARCH (Pitfall 1, CRÍTICO).
Output: `supabase/profiles-plan-privileges.sql` escrito, revisado (security + database) e APLICADO manualmente no banco live via SQL Editor.

NOTE: projeto NÃO usa `supabase db push` / migrations CLI — SQL é aplicado MANUALMENTE no Supabase SQL Editor (consistente com D-04). A task de apply é `checkpoint:human-action` ([BLOCKING]).
</objective>
